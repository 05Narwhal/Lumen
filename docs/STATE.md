- **Memories (Phase 6a).** `photos-core::memories` clusters one row per dated photo in Rust (22 ms for a real 34 k history, 60 ms for 250 k synthetic): sessions split on >12 h gaps; home = fullest ~5 km cell of the last year; **trip** = session of ≥10 photos whose located photos are mostly >50 km from home, named after the commonest place among those; **event** = a day of ≥12 photos within 2 km (≤2 per month, the busiest); **on this day** = ≥3 photos on today's date in an earlier year. Curation: `3·favourite + rating + sharpness/sharpest`, near-duplicates (dHash within 6 bits) −5, top `clamp(n/4, 8, 40)` curated. Sharpness and dHash come from the 256 px image at ingest (`photos-media::thumbs`) and are backfilled from thumbnails. `regenerate` replaces all rows in one transaction and keeps hidden ones by `(kind, start_at, end_at)`; it runs on the Maintenance lane (`maintenance::schedule_memories`) after each import and each six-hour tick. `LayoutScope.memory_id` is a memory's highlights. UI: Home carousel, `/memories` grouped by kind, `/memories/:id` (Highlights / All photos, Play, Hide), viewer `play=1` (4 s, crossfade). Replay the rules on real data with `LUMEN_DB=<copy of library.db> cargo test --release -p photos-core --test memories_real -- --ignored --nocapture` or `LUMEN_PHOTOS_SQLITE=<copy> … -p photos-import --test apple_library finds_memories`.
- **Slideshows (Phase 6b, spec §14).** `photos-core::slideshow` owns the document (`SlideshowDoc`: resolution, fps, optional `AudioTrack`, `Clip { asset_id, duration_ms, transition, motion }`), `normalized()` (clamps everything, including a pan that would show an edge), `timeline()` (`overlap_i = min(transition, dur_i/2, dur_{i+1}/2)`, so `start_{i+1} = start_i + dur_i − overlap_i`), `ease` (smoothstep) and `motion_at`, plus persistence and `from_memory`. **The preview implements the same maths in TypeScript** (`src/lib/slideshow-timing.ts`): a Rust test writes its answers to `src/lib/slideshow-golden.json` (regenerated like the ts-rs types) and the TS test is held to them, so canvas and MP4 cannot drift. `photos-media::slideshow` turns a document into one FFmpeg run (per clip `scale,crop,zoompan` with the eased expressions, `xfade` — `fade`/`slideleft`/`zoomin` — or `concat`, and `atrim,afade,volume` for audio); `src-tauri/src/slideshows.rs` renders each clip's edited still into `derivatives/tmp/slideshow-{id}` at twice the output's long edge, runs FFmpeg on the Import lane and reports `slideshow://progress` / `slideshow://finished`. **Frames (a clip is a layout, not a photo).** `Clip.frame` is `fill` / `blur` / `grid` and `Clip.extra` holds a grid's other photos (both `#[serde(default)]`, so documents saved earlier still parse as fills). `frame_layout(kind, aspects, frame_aspect)` returns the painter's-order `Placement`s — rectangles in frame coordinates, which may exceed the frame because covering crops — and **both** `photos-media::frame::compose` (the export) and `src/lib/slideshow-timing.ts` (the canvas) draw exactly those, held together by the golden file's `frames` cases. A portrait is never cropped: alone it is shown whole over a blurred, dimmed copy of itself, and two or three in a row share a grid (three when all are narrower than 0.62, so 9:16 phone photos fill a third each). `build(photos, style)` decides this from the catalogue's real shapes (`shapes_for`, orientation applied); `LayoutStyle` is Smart (default), Fill, Blur, Grid or Random, and Random is seeded from the asset ids so the same photos always give the same show. `rebuild_slideshow` is the editor's *Shuffle*. **Composition happens once per clip in Rust**, not in the FFmpeg graph, so a static backdrop is never blurred 30 times a second — the graph still takes one input per clip. Transitions are ten, one-to-one onto `xfade`: none/crossfade/fadeblack/fadewhite/slide/slideup/wipe/wipeup/circle/zoom. UI: `/slideshows` (rows, *New slideshow* via `components/photo-picker`, *From memory*, Delete with Undo) and `/slideshows/:id` (preview + transport, clip strip at 48 px/s with drag to reorder and edge-drag to trim in 100 ms steps, inspector with Frame and the ten transitions, *Shuffle frames*, autosave after 600 ms). Audio for the preview comes over `photos://slideshow-audio/{id}`. Measured on real photos: 12 originals (all portrait) → 6 grid clips, 21.0 s of 1080p in 24.8 s (0.85× real time, stills 7.6 s); as 12 fill clips it was 41.4 s in 70 s (0.59×). Duration matched the timeline exactly both times (`LUMEN_FFMPEG_DIR=<repo>/src-tauri/binaries LUMEN_SLIDESHOW_PHOTOS=<folder> cargo test --release -p photos-media --test slideshow_export -- --ignored --nocapture`; a release test build skips the `binaries` fallback, so set `LUMEN_FFMPEG_DIR` or an ancient FFmpeg on `PATH` is used).
- **Music (Phase 6c, roadmap §6.3).** **Lumen's only network feature, and it is off until the user opts in.** `src-tauri/src/music.rs` owns it: `search_url` builds the Jamendo v3 query, `parse_tracks` reads the response, and `usable` drops any `-nd` licence, because a no-derivatives track may not sit under a video (the picker can show them with `include_no_derivatives`). **Rust makes every request** — `music_search` and `music_download` are async commands and the preview plays over `photos://music-preview/{id}` (fetched once, last four kept in memory), so the webview never talks to Jamendo and the client id never leaves the backend. Without a key in Settings → Music (`settings.music.jamendoClientId`, a `PasswordInput`) no request is made at all. The id is the person's own (Settings → Music says so and links Jamendo's API terms); `parse_tracks` drops a track with `audiodownload_allowed: false`, and Find results carry *Music from Jamendo*. *Use* downloads into `<library>/music/{id}.mp3` beside a `{id}.json` sidecar holding title, artist, licence and the `credit` line; a track is always saved before a show uses it, so rendering never depends on the network. `list_saved` reads the folder (a file with no sidecar is listed as itself, which is how the user's own audio appears), and `photos://library-music/{name}` serves it — a file name only, never a path. An export writes the credit beside the film as `<export>.mp4.attribution.txt` (`slideshows::write_attribution` → `music::attribution_for`); a file the user brought themselves has nobody to credit and gets none. A show built from a memory opens with `music::track_for_memory` (the memory's id against the title-sorted list, so it always sounds the same), faded in 1 s and out 1.5 s; `from_memory` takes the track rather than choosing it, so `photos-core` still knows nothing about music. UI: `components/music-picker` (*In your library* / *Find music*, search, vibe and genre chips, play, *Use*, *Use a file…*), opened by the editor's *Choose music…*. Checks: `LUMEN_JAMENDO_CLIENT_ID=<key> cargo test -p lumen --test music_live -- --ignored` is the live round trip (**still unrun — it needs a key**); `cargo test -p lumen --test slideshow_music -- --ignored` exports a real MP4 with music and asserts the credit file, needing only FFmpeg.
- **Slideshow and memory polish (Phase 6d).** **Ordering:** `slideshow::arrange` keeps the day in order at the large scale and improves it inside a *moment* (a run with no gap over `MOMENT_GAP_S`, twelve minutes): the best photograph leads, near-duplicates are never adjacent, and photographs of a shape are emitted together so the grids fill. `orderables_for` reads the catalogue into `Orderable`s and `build_arranged` is what `from_memory` and `create_slideshow` use; *Shuffle* and Undo re-frame without re-ordering (`arrange: false`). **Six frames:** Fill, Blur, Grid (2–3 across), Quad (2×2), Feature (a hero over `FEATURE_WIDTH` with two stacked beside it) and Stack (two bands, the panorama layout). All four multi-photo layouts are one `cells` walk in Rust *and* in `slideshow-timing.ts`, held together by the golden file. **`Smart` reaches only for Stack**, because a panorama is badly cropped by 16:9; Quad and Feature buy density rather than fit (three 9:16 photos fill a 16:9 frame *exactly*, so a quad would show each at a third the size), so they belong to `LayoutStyle::Grid` and the editor's Frame control. `FrameKind::capacity` drives `normalized()`'s truncation of `extra`. **Twenty transitions**, each one-to-one onto an `xfade` name, each drawn by the canvas, with `GRID_SHUFFLE` (slices, bands, corner, open) chosen by `Random` whenever a grid sits either side of the join. **Curation** (`memories::curate`) is greedy maximum marginal relevance: quality minus how much a photograph repeats a moment or a place already covered. Redundancy is same place *and* same time, so the terms **multiply** — taking the larger made a memory shot in one spot look uniformly redundant. Looking near-identical is a veto, not a penalty. Sharpness enters as a rank where **ties share a rank**, or a library with no sharpness measured invents an order out of id alone. `score` means one thing for every photograph, curated or not: its own quality (250k synthetic: 19 ms). **Automatic music:** `music::pick_track` scores mood (doubled) against length, `music_for` asks the library first and then Jamendo when a key is set, and `SavedTrack.tags` keeps what a track was found by so the judgement needs no network. Below `PICK_FLOOR` the show stays silent. **Beat sync:** `photos-media::beats` decodes to mono PCM through FFmpeg, builds an onset envelope at 11.6 ms hops and reads tempo and phase by autocorrelation (the faster of a tempo and its double wins, or 160 BPM reads as 80); `slideshow::snap_to_beats` makes each clip's **advance** (`duration − overlap`) a whole number of beats — not its duration, which would leave cuts adrift by their transition's length — and `AudioTrack.start_ms` trims the track's head so the run starts on a beat. Below `MIN_CONFIDENCE` the show is left alone and `sync_slideshow_to_music` returns `no_beat`. The picker has a volume slider whose level becomes the show's `gain_db`. Checks: `cargo test -p lumen --test beat_sync -- --ignored` (synthesises click tracks; 90→90.7, 120→120.2, 140→139.7 BPM, cuts inside 15 ms, a drone refused at 0.02) and `--test slideshow_music -- --ignored` (renders a Quad and a Feature through FFmpeg with the credit file).
- **Slideshows, Round 4F (plan `2026-09-25-round-4f-slideshows.md`).**
  - **Automatic music searches all of Jamendo** (`music::music_for` over a `Searcher`; `Jamendo { client, key }` in the app). `queries_for` sends up to four queries at once (`search_many`, `futures_util::join_all`): two moods, each with and without the speed the pictures' energy asks for, instrumental, 60–140 % of the show's length. The best usable result is downloaded, or reused when it is already saved with its sidecar. The saved library is only the fallback when every search fails.   - **Export speed.** Each still is decoded once: `zoompan d=<frames>`, where looping the still had decoded, scaled and cropped the 4K JPEG for every output frame. Stills compose on a rayon pool of `still_jobs()` (≤ 6). The film renders in pieces (`photos-core::slideshow::segment_bounds`: frame ranges cut only where one photo is alone on screen; `photos-media::slideshow::render_slideshow_parallel`), joined with the concat demuxer (`-c copy`), with the audio muxed once. The encoder is the first of NVENC / QSV / AMF / VideoToolbox that FFmpeg lists **and** that passes a two-frame probe (`best_encoder`, cached per session), else x264. Quality is matched by PSNR (NVENC CQ 24 = x264 CRF 20). A hardware encoder gets at most 3 pieces, and a GPU export that fails is made again with x264. The setting is `playback.hardwareEncoding` (absent = on). **`concat` ends in `settb=1/{fps}`**: a cut followed by a transition did not render at all before. - **Music that fits, videos in slideshows, Round 6 (spec `2026-10-04-music-and-video-shows-design.md`, plan `2026-10-04-round-6-music-and-video-shows.md`).** Migration **0028** (`track_profiles`, `video_highlights`; 0027 is the parallel session's `develop_drafts`).
  - **Music chosen by listening.** `photos-core::music_profile::profile` measures mono PCM (one decode with the beats: `beat_analysis::analyse_keeping_samples`): tempo, onsets/s, brightness (spectral centroid, log 250 Hz–4 kHz), loudness and dynamics (spread of a 0.5 s dB curve), and **sections** (loudness/brightness novelty over ±4 s, ≥ 8 s apart, snapped to downbeats). `music::music_for` searches (`queries_for`: all `relevance`, later queries on a seed-dependent `offset`; `wider_queries_for` when fewer than `MIN_SHORTLIST` survive), **drops every track another slideshow or memory film plays** (`slideshow::music_in_use`, except the memory's own film), shortlists `SHORTLIST` = 6 by tags and length, fetches and measures each (`Searcher::fetch` + `track_profiles::measure_bytes`, three at a time), and ranks by `suits_heard` = 0.5 · `sound_fit` (distance to `MOOD_SOUND` targets blended by the photos' mood weights) + 0.3 · `mood_fit` + 0.2 · `length_fit`. Only the winner is saved; its profile is cached (`track_profiles::remember`). Offline, saved tracks not in use are ranked by their cached profiles. Unheard candidates (no FFmpeg) fall back to tags.
  - **The part of the song.** `music_profile::choose_window` picks a start at the top or a section start (never in silence) that holds the loudest section, ends near a boundary when it can (fade 1 s, else 2.5 s; mid-song starts fade in 0.4 s). `build_for_memory` applies it to `AudioTrack.start_ms`; the editor asks `music_window` when music is chosen and on *Best part* (*Plays from m:ss*). `snap_to_beat_grid` now trims to the first beat at or after `start_ms`; `normalized()` allows `start_ms` up to 30 min.
  - **Videos.** `Clip.video: Option<VideoSpan { in_ms, out_ms }>` (skipped when absent, so photo documents and the golden file are unchanged). `photos-media::video_frames` samples at 2 fps (sparser past 5 min), 192 px wide, tone-mapped when HDR, and measures sharpness (Laplacian variance), luma, clipping, motion and cuts (24-bin histogram distance > 0.5); `loudness_at` reads the sound at 8 kHz. `video_highlights::analyse` adds faces (YuNet) and CLIP aesthetic (every second sample) when ready — the analyser name (`frames@1+faces+clip`) re-scores when a model arrives — and `video_highlight::best_window` takes the best 3–6 s inside the trim, off the first/last 0.3 s, never across a cut. Backfill `maintenance:video-highlights` after import and on the maintenance tick; a re-trim (`save_edit`) forgets the highlight. Videos are always alone (`choose_frame`/`group_frame`/`group_moment`), Fill or Blur by shape, no Ken Burns, muted; their score is 0.5 + 0.5 · highlight. Memories use `with_ready_videos`; `create_slideshow` and the editor's *Add photos or videos…* (`slideshow_clips`) find highlights first; *Shuffle* keeps hand-set spans; the inspector has *Starts at* and *Best part* (`video_best_part`). Candidates: videos, Trash, concealed (Hidden folder / hiding albums) and photos without a hash are left out altogether. **Edges:** a time sweep (≤ 10 s apart, hash ≤ 6 bits) judged *Exact* (same second, hash ≤ `EXACT_BITS` 2, same aspect ±1 %, not burst frames, CLIP ≥ `EXACT_COSINE` 0.98 or, without embeddings, two informative hashes, **and** pixel difference ≤ `EXACT_PIXEL_DIFF` 1.5) or *Similar* (CLIP ≥ 0.985, or without embeddings hash ≤ 4 within 3 s); a hash-slice pass (four 16-bit slices) for Exact copies whose dates differ or are missing. Never paired: an asset and its `derived_from`, a RAW with a non-RAW, an original with a file an editor wrote (Lightroom, Photoshop, …), a dismissed pair, hashes with < `MIN_HASH_BITS` 10 set or clear bits. **Sets:** union-find, strongest edges first; a join is refused when it would put a dismissed pair together or any cross pair has cosine < `SET_COSINE` 0.90; a set with any Similar edge is *Similar*. **Keeper order:** not an export, more pixels, RAW > HEIC/PNG/TIFF > JPEG, sharper, edited, rated or favourite, more albums, lower id. **Resolve** (`resolve_all`, one transaction for the whole batch, every set checked first): the keeper takes the removed photos' albums, favourite, max rating, label/flag if empty, keywords union, title/caption if empty; the rest go to the Trash; only photos *this call* moved are in `ResolveUndo.removed`, so Undo never restores a photo that was already trashed. Faces stay with their photo. **Cache:** `SETS` keeps the last answer per library and `changes.version`; a dismissal clears it. UI: Home card (`DuplicatesCard`), `/duplicates` (`DuplicateSetRow`, *Remove exact copies*, *Remove all suggested*, Undo toasts), palette *Find duplicates*. **Real-data replay:** `LUMEN_DB=<copy> LUMEN_LIBRARY=<library> [LUMEN_SHEET=<png>] cargo test --release -p lumen --lib exact_pixels_on_a_real_library -- --ignored --nocapture`; timing: `cargo test --release -p photos-core finds_sets_at_250k -- --ignored --nocapture` (651 ms).

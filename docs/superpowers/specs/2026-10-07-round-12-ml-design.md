## Why

r1 trained the 11B Retouch network on 493 synthetic pairs from Wikimedia finals for 10 h 38 min:

| | val ΔE | crop IoU |
|---|---|---|
| untouched | 6.97 | — |
| best ΔE (step 1351, epoch ~193) | 4.02 (not saved) | 0.171 |
| `best.pt` (lowest val loss, epoch ~91) | 4.14 | 0.184 |
| `last.pt` (epoch 240) | 4.14 | 0.171 |

What it means: the network learned the synthetic correction (ΔE −40 %), it is data-bound (train 3.74 vs val 4.14), its crop head learned nothing (IoU fell from 0.20 to 0.17), and it has never been compared with *Auto*. Training ran at ~3 photos/s with the GPU at 99 % and 13 GB for a 2.3 M-parameter model: the cost is the differentiable render and loss, not the network.

So the model becomes **Auto v2** (technical correction; tone and colour), improved by more and better data and a much faster kit, and is tested in the app behind **Experimental** switches before anything replaces classic Auto. Creative Retouch (styles) waits for real pairs and 8f.

## §1 Training speed
- **Measure first.** `python -m lumen_train.retouch.bench` runs ~30 steps with `torch.profiler` and prints: data time vs step time, the top CUDA and CPU ops, kernel launches per step, peak VRAM; it writes a Chrome trace to the run folder.
- **Approach A (chosen):** the dataset only loads the cached 256 px input (optional RAM cache: 20 k items ≈ 8 GB fp16). Synthetic damage, its render and the loss run **batched on the GPU** in the training step (`synth.make_batch(final, gen, device)`). Python loops in `render.py` (curve channels, HSL bands, grading wheels) are vectorised. The training loss can use **OKLab distance** (`loss.train_metric = "oklab"`), switching to ΔE2000 for the last `loss.de2000_tail` share of epochs; validation always reports ΔE2000. Validation every `train.val_every` epochs (default 1; 2–5 on big data).
- Rejected: precomputed damage on disk (fixed variety, disk); multiprocessing workers on Windows (measured slower).
- **Checkpoints:** `best.pt` (val loss), **`best_de.pt`** (val ΔE2000), `last.pt`. `log.csv` keeps every epoch (it already does).
- **Acceptance:** the r1 configuration (493/77, 240 epochs) runs in **≤ 45 min**; its best val ΔE stays within noise of r1 (≤ 4.25); the golden render test still passes within 1/255.

## §2 Data catalog
- `python -m lumen_train.data add <name> <folder> --kind finals|pairs|raw|raw+jpeg --licence "<text>" [--commercial] [--attribution]` registers a local source in `<root>/sources.toml`; public sources stay in the repo's `datasets/registry.toml`. The licence gate reads both; a name in both is an error.
- `data prep [<name>…] [--clip] [--jobs N]` prepares only new or changed files (content SHA-256 in `<root>/<source>/index.jsonl`) by calling the app's `retouch_prep`; it never writes beside an original.
- `data status` prints items per source × split (train/val/test), CLIP coverage and licence.
- `data download wikimedia --limit N` wraps the existing downloader (Featured + Quality, BY-SA skipped, 1280 px thumbnails).
- **Splits** are a pure function of the photo's **stem** (file name without extension, lower case, with suffixes like `-edit`, ` copy`, `-2` stripped by one shared `stem()`), so they never change when data is added, and `IMG_1234.jpg` and `IMG_1234.CR3` always share a split. Test: `sha1("test|"+stem) % 1000 < test‰`; otherwise val by the existing rule. Shares per source in the registry (`split = { val = 15, test = 2 }` default; contributor's sources `{ val = 12, test = 18 }`, ≈ 30 test photos never trained on).
- `train init=<ckpt>` warm-starts the weights (fresh optimiser and schedule); `train sources=all` means every prepared source (only commercial ones with `--ship`).

## §3 Auto v2 recipe
- **Data:** Wikimedia Featured + Quality to 10–20 k photos; the contributor's finals (`contributor-finals`) now; Friday's RAW + JPEG pairs (`contributor-pairs`), which are also what makes RAW input familiar (unedited RAWs stay out: as synthetic finals they teach that a flat render is the goal); **~15 % "already fine" samples** (`synth.identity_p = 0.15`: no damage, the target is the input).
- **Friday pairs without XMP:** `build_pairs.py --align` renders the RAW with Lumen's defaults (`render_recipe`, ~1024 px), estimates the similarity transform to the edited JPEG on gradient images (OpenCV ORB + RANSAC; opencv-python is Apache-2.0 and stays in the training kit), and records the **human crop box and angle** in the RAW's frame. A pair with too few inliers is skipped with its reason. The ΔE target is the JPEG mapped into the crop frame; the slider targets stay unknown (`v_known = 0`) except geometry. These are the first real crops the crop head sees.
- **CLIP on:** `data prep --clip` for every source; the 15 % dropout stays.
- **Model:** the r1 architecture first (fair comparison), plus `model.width` (1 or 2) for a scaling test once there are more than 10 k photos.
- **What Auto v2 applies in the app:** tone and colour only (Basic, curve, HSL, grading). Never crop, straighten or masks.
- **Ship bar:** lower ΔE than classic Auto on the **test** split of every source, and better-or-same on ≥ 80 % of a blind sheet of the contributor's test photos plus ~50 of Julian's photos (copied by him into `C:/lumen-train/eval-library/`).

## §4 Experimental in Lumen
- `SmartSettings.experimental: Experimental { auto_model: bool, retouch: bool }`, both default false (additive serde field; old settings files read as off).
- **Dev models folder:** `config_dir/JL-Studios/Lumen/models/dev/`. `export.py --install-dev` writes `<role>-dev.onnx` and `<role>.json`:
  ```json
  { "id": "retouch-dev-2026-10-12-r2", "role": "retouch", "file": "retouch-dev.onnx", "bytes": 0, "sha256": "…",
    "licence": "Lumen (own weights)", "retouch": { "size": 256, "layout": 1, "inputs": ["image", "clip", "clip_flag"], "output": "v" },
    "trained": { "run": "r2", "val_de": 3.81, "sources": ["wikimedia-cc0-pd", "contributor-finals"] } }
  ```
  Inputs: `image` `(1,4,256,256)` float32 = `photos_media::retouch_input::prepare`'s encoded colour + validity channel (the `input.u16` layout / 65535), `clip` `(1,512)`, `clip_flag` `(1,1)`; output `v` `(1,len(PARAMS))` in [0,1]. The model computes its own statistics from `image`. It is a `ModelEntry` plus `trained` (ignored by the app except for display). The app verifies the sha on load. A dev entry is used only while its feature's switch is on; a `layout` other than `photos_core::retouch::RETOUCH_LAYOUT` is the state *made for another Lumen*.
- *Auto uses the trained model:* the model's tone/colour slots become Auto's prior; the existing aesthetic search refines Basic from there when smart features are on. `AutoResult.source = "model" | "classic"`.
- *Retouch:* the button beside Auto (11B Tasks 9 and 11): every panel including crop/straighten and the two gradients, one history step. The personal layer (11B Task 10) waits until the model is stable.
- Each Experimental row shows the model state: *not found* / *ready · r2 · ΔE 3.81* / *made for another Lumen* / *failed: <reason>*.

## §5 AI progress
- One mechanism for every interactive AI action, generalised from denoise's progress/cancel: Rust `ai_task` module with `AiTask::new(app, feature) -> (task, CancelToken)`, `task.stage(label_key, done, total)`; events `ai-progress { task, feature, stage, done, total }` and `ai-finished { task, feature, ok, cancelled }`; command `ai_cancel(task)`. Commands that run AI take `task: Option<String>` from the frontend so the UI knows its id before the first event.
- Frontend `src/components/ai-button/` (`gui.tsx`, `styles.scss`, `index.ts`) and `src/hooks/use-ai-task.ts`. The button **is** the progress: after **250 ms** without a result, its label crossfades to the stage (*Reading photo… → Trying looks 2/3 → Applying*), a determinate ring traces its border (`--ai-progress` custom property on a conic-gradient mask), with a soft shimmer while `total` is unknown. Hover shows *Cancel*; a click cancels. Reduced motion: no shimmer, text only. Colours, durations and radii are tokens in `globals.scss`. Reviewed with the `apple-design` skill.
- Used by Auto, Retouch and denoise. Background ML (OCR later) stays on the activity ring.
